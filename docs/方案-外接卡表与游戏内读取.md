# 方案：外接卡表 vs 游戏内读取（调研与取舍）

> 结论先行：**不建议"只返回名字、全部靠外部表"**。名字本来就能从游戏零成本拿到且绝对准确；
> 真正缺的是"文本与数值"，而游戏内已经覆盖了约 86%。合理的做法是
> **把缺口外置到一张统一的知识表**，其余继续读游戏——即"混合 + 知识层外置"，不是替换。

---

## 二、三个方案对比

### 方案 A：只输出名字，全部外接卡表
插件退化成"状态转储器"，把所有实体名替换成英文/中文名，一切解释靠离线表。

- ✅ 单一事实来源，prompt 组装全在离线侧，插件代码最薄。
- ❌ 需要为 **436 张卡 + 39 冲突 + 47 空间 + 18 科技** 全部建表，其中 386 张卡游戏内本来就有现成文本，等于把免费且精确的数据重做一遍。
- ❌ 译名风险：外部表用英文名，游戏用官方中文名，中间靠 `en_US title → image → zh_CN title` 桥接；一旦某个卡的英文标题与外部表写法不一致（标点、大小写、扩展后缀），就会静默丢失。
- ❌ 维护成本随每次扩展线性增长，而游戏内文本是自动跟随版本的。

**判断：不划算。** 真正省下来的只有插件里那点解析代码，代价是数据面全量冗余。

### 方案 B：现状（纯游戏内）
- ✅ 零维护，跟着版本走。
- ❌ 基础包 43 张、冲突奖励、空间效果、卡牌费用四个缺口永远补不上，而它们恰好是"该打哪张牌/该抢哪场冲突"的核心依据。

### 方案 C：混合 + 知识层外置（推荐）
游戏内优先，缺口用一张统一的外部知识表补，二者用 **英文标题** 作唯一连接键。

- ✅ 免费的继续免费，只维护 4 类缺口（约 100 条，不是 500 条）。
- ✅ 连接键已被验证：`en_US` 的 `card.<set>.<image>.title` → image → `zh_CN` 同名键 → 官方中文名，
  本轮补基础包 54 条时 100% 命中，没有再出现"手写译名对不上"的问题。
- ✅ 一个表管所有类型（卡/冲突/空间），后续扩展只需追加行。

## 三、推荐架构

```
                    ┌─────────────────────────────┐
                    │ 知识表 mods/ai/kb.tsv        │  ← 人工/公开源维护，按英文标题索引
                    │ en_title|type|cost|agent|... │
                    └──────────────┬──────────────┘
                                   │ 只填缺口
游戏运行时 ──► 实体解析 ──► 组装 prompt
   │              │
   │              └─ 名字：本地化（永远用这个）
   └─ 文本：本地化 → 知识表 → 仅名字（逐级降级，不编造）
```

### 解析优先级（每个字段独立降级）

| 字段 | 第一优先 | 第二优先 | 兜底 |
|---|---|---|---|
| 名字 | 本地化（GUID/image） | 知识表 en_title 反查 | 短 ID |
| 效果文本 | 本地化 | 知识表 | 不写 |
| 费用 | 知识表（游戏导出为 null） | — | 不写 |
| 冲突奖励 | 知识表 | — | 只写冲突名+等级 |
| 空间效果 | 知识表 | — | 只写空间名 |

关键约束：**任何一级查不到就不写，绝不编造**。这条已经在现有实现里成立，继续保留。

### 知识表规范（一张表覆盖所有类型）

`mods/ai/kb.tsv`，`#` 开头为注释，制表符分隔：

```
en_title  type  cost  agent  reveal  notes  source
Worm Riders  imperium  6  "特使：城市/厄拉科斯；香料2"  "剑4（弗雷曼≥2，同盟再+2）"  "高价值战斗牌"  public-card-db
Secure Imperial Basin  conflict  -  "1st: 1VP+控制帝国盆地"  "2nd: 水2"  "3rd: 水1"  public-card-db
```

- `type` 决定该行怎么用（imperium/intrigue/conflict/tech/space/leader/contract）
- `cost` 用整数或 `-`
- 空字段表示"此源没有该信息"，不得填猜测值

现有的 `card_text_extra.tsv`（54 条）已经符合这个格式的子集，迁移成本≈0，只需加列。

## 五、绕不开的风险

1. **来源可信度**：公开卡表是玩家整理，可能有错。缓解：`source` 列记录出处；关键数值（VP/费用）抽样核对规则书 PDF。
2. **版本漂移**：扩展更新后外部表会落后。缓解：知识表只覆盖"游戏内没有的"，游戏内能读的永远优先，因此版本更新不会让整体变差。
3. **合规**：抓取第三方站点需遵守其条款，建议只人工整理/少量取用，不做全站镜像。
4. **译名桥接**：已用「英文标题 → image → 官方中文」验证可行；若某卡英文标题在外部表写法不同，会静默丢失——需要一条"外部表命中率"日志来监控（当前 `withEffect` 计数可扩展为 `kbHit/kbMiss`）。

## 六、验收标准

- 覆盖率：帝国牌「有文本」从 109/174 提到 ≥ 160/174（补完 25 张后），冲突牌 33/33 有奖励，科技 18/18。
- 正确性：随机抽 10 条知识表记录，与规则书/游戏内表现逐条核对。
- 稳定性：日志里 `kbHit` 与 `kbMiss` 可查，命中率低于阈值时能在日志里看出来。

---

## 七、对"只返回名字"这个想法的最终判断

想法本身方向是对的——**让插件只负责"是什么"，让数据负责"怎么样"**。但"全部外接"过头了：

- 名字：游戏内零成本、绝对准确，没有理由外置；
- 文本：游戏内覆盖 86%，外置等于重做；
- 真正该外置的是 **游戏内根本不存在的东西**（基础包文本、冲突奖励、空间效果、卡牌费用）。

所以最终方案 = 保留现有解析，把上述四项塞进 `mods/ai/kb.tsv`，用英文标题做连接键，
逐字段降级、查不到就不写。这比"全外接"少做 400 多条数据，且不会因为外部表过期而整体退化。

## 八、落地进度（10-31 深夜，build 2026-10-31h 前）

### 已完成：防漏机制（不依赖外部数据）

1. **父实体回退**：能力实体（`FamilyAtomicsAbility`、`DeployUnitsAbility`…）没有独立文案时，
   沿 `Entity.Parent` 上溯 1–3 层，取所属卡/领袖的效果。纯游戏内数据，能吃掉最大一块缺口。
2. **`〔效果待查〕` 显式标注**：查不到文本时不再沉默——沉默会被模型误读成"这牌没效果"。
3. **`dump/ai/gaps.txt`**：把缺文本的实体按出现次数落盘，洞从"感觉有"变成可数清单。
4. **`mods/ai/kb_extra.tsv`**：按中文名索引的知识表（冲突/空间/科技/合约），已接入合并管道；
   `mods/ai/kb_todo.tsv` 自动列出 89 条待补（39 冲突 / 46 空间 / 4 科技）。
