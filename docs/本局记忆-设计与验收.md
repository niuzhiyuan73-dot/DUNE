# 本局记忆（事件流）· 设计与验收

日期：2026-11-01
代码：`ai_probe/Memory.cs`（新增）、`ai_probe/State.cs`（新增 `Snapshot` / `Capture`）
契约验收：`python -X utf8 -B mods/tools/verify_memory.py`（24 项）

## 一、为什么必须先做事件流

模型每次请求都是无状态的：同一局里，它对同一个冲突可以给出两种不同解读。
要让它"记得"，最直接的想法是把之前的问答塞回 `messages`——但那会带来两个问题：

1. **把建议当成事实**：我建议"买沙虫骑士"，它下次就以为已经买了。
2. **不可审计**：历史消息是隐性状态，出问题只能猜。

所以这里的顺序是反过来的：**先有"发生了什么"的事件流，才有记忆**。建议只作为建议单独存放。

## 二、事件从哪来

不新增任何游戏内钩子，全部来自**同一玩家两次决策之间的快照差分**：

```
决策 A → State.Capture(玩家) → 存快照
决策 B → State.Capture(玩家) → 与 A 比较 → 产出事件 → 更新快照
```

快照只收「可比较的标量」：胜利点、四阵营影响力、四阵营同盟、手牌/牌库/密谋/弃牌数量、
可用特使数、当前冲突名。

取不到就标未知并跳过该字段的差分——**不把"读不到"当成"变成 0"**。
例如开局领袖指派阶段 `RemainingAgents` 会抛 NRE，此时 `AgentsKnown=false`，这一项不参与比较。

## 三、会产出哪些事件

| 触发 | 产出文本（示例） |
|---|---|
| 冲突名变化 | `【第2轮】新冲突：厄拉奇恩之战` |
| 胜利点变化 | `第2轮：胜利点 1→3（+2）` |
| 影响力变化 | `第2轮：弗雷曼影响力 1→2（达到 2 点，应得 1 胜利点）` |
| 同盟变化 | `第3轮：获得皇帝同盟` / `第3轮：失去姐妹会同盟` |
| 牌组总数变化 | `第2轮：牌组总张数 13→14（具体是哪张无法确认）` |
| 密谋数量变化 | `第2轮：密谋手牌 2→3` |
| 特使全部回收 | `第2轮：特使已全部回收（可用 4）` |
| 收到建议（后台线程） | `曾建议（未确认执行）：第2轮：选择「渗透」…` |

上限：事件 8 条、建议 3 条、整块 **≤ 520 字**。超预算时保留较新的，并显式标注「较早的已省略」。

## 四、明确不做的三件事（都是刻意的）

1. **不猜"获得了哪张牌"**。手牌每轮全部更换，前后差集没有意义；只报牌组总数变化并注明未知。
2. **不把建议写成已执行**。建议单独一段、带轮次前缀、前缀写明「未确认执行」。
3. **不跨局**。以 `match` 对象指针为键，新对局自动新建并打日志 `[MEMORY] 新对局，记忆已重置`。

## 五、在提示词里的位置

```
AI 玩家：X（第 N 号选择）
【局势】…          ← 当前完整局面
【本局记忆】…      ← 新增：已发生的变化 + 曾建议
【相关机制】…      ← 按需机制（最多 3 条）
待选列表：…        ← 本次选项
```

放在局势之后、选项之前：先让模型知道"现在是什么样"，再告诉它"刚发生了什么"，
最后才给选项。记忆不进系统提示——系统提示要保持稳定前缀，才能吃到上下文缓存。

日志里也存了 `memory` 字段，可逐条核对"当时到底给了什么记忆"。

## 六、隔离与重置

| 维度 | 做法 |
|---|---|
| 对局 | `match` 指针为会话键；换局即新建 |
| 玩家 | 按 `PlayerName` 分桶，互不串味 |
| 线程 | 游戏线程做快照差分，后台线程记建议，共用一把锁 |
| 手动 | `Memory.Reset()` |

## 七、验收

### 已自动验证（24/24 PASS）

`verify_memory.py` 做源码级契约检查，覆盖四类：

- **硬约束**：事件/建议上限、字符预算 ≤ 800、失败返回 null 不阻断决策。
- **语义约束**：含「只含已确认发生的变化」「未确认执行」「具体是哪张无法确认」等措辞，
  防止后人改代码时把"建议"悄悄写成"事实"。
- **链路完整性**：`Plugin → Memory.Update → Coach.Observe → Send → Append(jsonl)`，
  以及 `Append → Memory.NoteAdvice`。
- **段落顺序**：局势 → 记忆 → 机制 → 待选，用源码位置断言。
- **不越界**：`Memory.cs` 内不出现任何写游戏状态的方法名。

### 待实机验证（下一局）

1. 日志出现 `[MEMORY] 新对局，记忆已重置 (match=…)`。
2. 首份记忆的 `[MEMORY] diag` 行里 `vp / agents / conflict` 都有真实值（不是 0/null）。
3. `coach_*.jsonl` 的记录里 `memory` 字段非空，且内容只包含确实发生过的事。
4. 重点抽查：**建议段落是否始终标注「未确认执行」**——这是最容易被模型误读为事实的地方。

## 八、一致率采集（已接入，等实机出数）

记忆只回答"我建议过什么"，不回答"它照做了吗"。补这一环不需要改决策链路，只要**记下 AI 真正选了什么**：

- `ai_probe/Actual.cs`：在 `WormAIProfile.MakeChoice` 的 **postfix** 里取返回值
  （`ISelectionCounter`），按 `[ThreadStatic]` 的决策序号挂到对应记录上；
  返回值先试白名单属性（Selection/Entity/ID…），拿不到就退化成 `ToString()`。
- 只记录、不修改、不参与决策。结果写进 `jsonl` 的 `actual` 字段，与 `answer` 同条。
- 判定放在离线：`python -X utf8 -B mods/tools/coach_agreement.py`
  - 从 `pending` 抽候选名 → 答案里最先出现的候选名 = 建议对象；`actual` 里出现的候选名 = 实际对象；
  - 两边都定位到才计入分母，定位不到记 unknown 单独统计；
  - 同名多实例（渗透×2）视为同一项——它们本来就没有区别。

**已知的方法学限制**：建议是异步返回的（1–3 秒），而 AI 在 0–400 ms 内就决策完了，
所以建议**从不影响**本次选择。一致率只说明"教练与 Hard 档权重是否同向"：
高不证明建议对，低也不证明建议错。这一点必须写在结论里，否则数据会被误读。

匹配器已在历史日志上验证过覆盖率：131 条可抽候选的样本里，128 条（97.7%）能从答案定位到候选名。

## 九、局限与下一步

1. **不知道玩家是否采纳**：已由第八节的 `actual` 采集补上，待实机出数。
2. **不记录对手动作**：目前只跟踪当前决策者本人的快照。对手的 VP/影响力在【局势】里可见，
   但没有事件化，所以"上家刚抢了弗雷曼轨道"这类信息不会进入记忆。
3. **轮次靠冲突变化推断**：本玩法固定 10 场且不重复，推断成立；换成可循环冲突的玩法需要改成显式轮次。
4. **建议与记忆未联动**：记忆里存的是"曾建议"，但没有把"建议被否定后改口"记录下来——
   若做第二版记忆，应允许同一计划被后续事实覆盖，而不是叠加多条互相矛盾的旧计划。
