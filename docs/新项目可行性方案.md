# 从零开发一款「牌库构筑 + 工人放置」游戏的可行性方案

**版本**：v1.0　**日期**：2026-10-30
**依据**：本项目对《Dune: Imperium》数字版的逆向分析结论（286 张卡牌视图注册表、13 份剧本 JSON、三层封闭模型实证）

---

## 0. 结论先行

**可行，且属于"一个人能做完"的量级——前提是三件事必须一开始就定死。**

| 判断项 | 结论 |
|---|---|
| 技术可行性 | **高**。回合制、无实时同步、无物理/3D 刚需，纯 Web 技术栈即可覆盖 |
| 规则复杂度 | **中等**。核心规则约 25–35 条，效果原语约 28 个，远低于 CCG（万智牌 2 万+ 卡） |
| 内容工作量 | **这是真正的成本中心**，不是引擎。100 张卡的内容实现 > 整个引擎 |
| 单人可完成性 | **可以**。基准 9 个月（含 AI 对手），3 人团队基准 5.5 个月 |
| 最大风险 | 不是技术，是**单人 AI 质量**和**卡牌平衡的长尾** |
| 建议起步动作 | 不写代码，先写一份可执行的规则书 + 30 张卡的纸质/无界面原型 |

**三个必须一开始定死的决策：**

1. **不做 1:1 复刻，做"骨架保留、皮肤原创"** —— 规则机制本身不受版权保护，但 Dune 的名称、角色、图像、卡表全部受保护，且 286 张卡的效果实现是全项目最贵的一块。
2. **效果必须是数据，不是代码** —— 这是本项目逆向工作给出的最贵教训（见 §1），也是新项目唯一的结构性优势。
3. **先做单人 vs AI 的完整闭环，联机后置** —— 数字版桌游 80% 的游玩时长在单人；联机是放大器，不是地基。

## 1. 先回答"为什么不在现有游戏上继续"

这不是路线偏好问题，是已实测的**结构性封闭**。本项目 v38→v61 共 24 个插件版本，七条技术路线全部撞墙，根因是一个三层模型：

```
身份层  编译期卡类     ← MakeArchetypes<T>() 反射扫描，只在启动跑一次
规则层  AbilityID      ← 每个能力是硬编码 C# 类，GetAbilityID() 返回字面量
表现层  ArchID → 预制体 ← 286 条映射，预制体烘焙了图形/费用/文字
```

三层都是**编译期常量**，不是运行时数据。数据层（剧本、起始牌组、起始资源、本地化）完全开放，但卡牌定义本身封闭。要真正新增一张卡，必须同时改 metadata 类型表 + 代码段机器码 + 资源映射表——等于重写游戏的一部分，且每次官方更新后重做。

**这个结论对新项目的价值，不是"此路不通"，而是三张施工图：**

- 官方把「身份 / 规则 / 表现」分成了三层，说明这个分层是对的，但要**全部做成数据**；
- 官方规则层硬编码导致"改一张卡的费用"都需要逆向，说明**效果系统的可表达性**决定了这个项目的长期成本；
- 官方存档是明文 JSON，含 `entities` + 803 条 `displayActions` 动作历史，**反证了事件日志式存档是可行的**——我们直接采用，不重复试错。

> 一句话：现有项目已经替新项目付完了"领域建模"的学费，只是没法把学费换成代码。

## 2. 整体玩法与核心机制的目标定位

### 2.1 保留什么（骨架，这五条是这个品类的灵魂）

| 机制 | 保留理由 | 不保留会怎样 |
|---|---|---|
| **牌 = 行动点**（每张牌既是资源又是行动） | 这是 DBG 与 WP 的粘合点，一个选择同时影响两条曲线 | 退化成"打牌"和"放工人"两个独立小游戏 |
| **工位稀缺 + 抢先占位** | 玩家间唯一的直接对抗来源（间接互动） | 变成四人单机，竞速感消失 |
| **回合内 Reveal 的信息博弈** | 手牌是隐藏信息，揭示顺序制造决策张力 | 变成完全信息博弈，AI 变简单，人也变无聊 |
| **影响力轨道 + 联盟** | 中期目标层，给"长期投资"一个理由 | 只剩买牌一条成长线，中期空转 |
| **冲突的胜者/次席双档结算** | 让"不赢也有收益"，降低挫败、提高参与率 | 战斗变成全有全无，弱者直接放弃 |

### 2.2 改什么（皮肤与简化）

| 项 | 原版 | 新项目 | 理由 |
|---|---|---|---|
| 主题 | 沙丘 IP | **原创**（见 §2.3 候选） | 法律边界 |
| 卡池 | 286 张（含 3 扩展） | 首版 60 → 1.0 版 90–120 | 内容是成本中心，先做窄而深 |
| 派系 | 4 个 | 4 个（不变） | 4 是"能记住"的上限，少于 4 张力不足 |
| 胜利点 | 10 | 10（可配置 8/12/15） | 阈值为剧本参数，一线可调 |
| 表现 | 3D 棋盘 + 动画 | 2D 卡面 + 轻动效 | 3D 是成本黑洞，回合制不需要 |
| 单局时长 | 45–90 分钟（实体） | **20–30 分钟** | 数字版自动结算的红利，也是移动端的前提 |

### 2.3 主题候选（选择标准：能否自然解释"稀缺工位 + 派系影响力 + 争夺式冲突"）

| 方向 | 工位如何自洽 | 派系如何自洽 | 风险 |
|---|---|---|---|
| **深海打捞 / 沉船探索** | 沉船残骸点有限，先到先得 | 打捞公司 / 海军 / 黑市 / 学界 | 冲突动机较弱 |
| **商路帝国 / 丝路贸易** | 驿站、关卡、港口有限 | 商会 / 军阀 / 教团 / 王室 | 战斗需要额外包装 |
| **修仙宗门**（推荐） | 灵脉、洞府、秘境名额稀缺 | 四大道统 / 世家 / 散修盟 | 美术风格需统一 |

推荐**修仙宗门**：灵脉（工位）天然稀缺、四派系影响力天然对立、"秘境争夺"可直接承载冲突结算，且中文语境下的美术与文案成本最低。

### 2.4 内容规模基线（首版）

| 内容 | 数量 | 说明 |
|---|---|---|
| 帝国牌（可购买） | 60 → 90 | 每局市场可见 6 张，60 张可支撑约 40–60 局不明显重复 |
| 起始牌 | 10 种 | 每人固定 10 张，5 种基础 + 变体 |
| 阴谋牌（反应式） | 24 | 隐藏信息的主要载体 |
| 冲突牌 | 16 | 每局翻 1 张 × 8–10 回合 |
| 领袖 | 8 | 决定开局策略，是重玩性的第二来源 |
| 工位 | 20–24 | 棋盘主体 |
| 派系轨道 | 4 | 每轨道 2–3 档奖励 + 联盟 |

## 3. 拟采用的开发方式与所需资源

### 3.1 技术栈选型

| 方案 | 优势 | 劣势 | 适配度 |
|---|---|---|---|
| **TypeScript + React + Node**（推荐） | 引擎与渲染分离干净；headless 引擎可直接在 Node 跑批量对战；热更新；一套代码上 Web / 桌面 / 移动 | 无 3D 观感 | **首选** |
| Unity (C#) | 若未来要 Steam 3D 表现 | 迭代慢、包体大、内容热更麻烦；且本项目已证明 Unity 逆向调试成本极高 | 次选 |
| Godot | 轻量、开源 | 生态与素材少，UI 系统不如 Web 灵活 | 备选 |

**推荐组合**：`TypeScript` 全栈 + `React` 渲染 + `Zustand/Redux` 状态 + `Vite` 构建 + `Node/Express` 服务端（后置）+ `SQLite`（本地）/ `PostgreSQL`（线上）。

**关键约束**：核心引擎必须写成**零渲染依赖的纯 TS 包**，能直接在 Node 里以 headless 方式跑完整对局。这一条决定了后面 AI 训练、平衡测试、回归测试能不能做——这是整个技术方案里最重要的一条。

### 3.2 架构分层

```
┌─────────────────────────────────────────┐
│ 表现层  React 组件 / 动画 / 音效          │  ← 只读 state，只发 command
├─────────────────────────────────────────┤
│ 交互层  Command 构造 / 合法性预检 / 提示   │
├─────────────────────────────────────────┤
│ 规则引擎  State + Reducer + 事件队列       │  ← 纯函数，无 IO，无随机源
│          ├ 回合状态机（5 阶段）            │
│          ├ 时序解析器（同触发点排序）      │
│          └ 效果解释器（读卡牌数据）        │
├─────────────────────────────────────────┤
│ 内容层  cards.json / conflicts.json       │  ← 数据，不是代码
│          leaders.json / board.json        │
├─────────────────────────────────────────┤
│ 基础层  seeded RNG / 事件日志 / 快照       │
└─────────────────────────────────────────┘
```

### 3.3 效果系统的关键决策（决定项目生死）

原版把每个能力做成硬编码 C# 类，代价是"改一个数字要逆向"。新项目必须反过来：

**卡牌 = 数据 + 解释器**

```jsonc
{
  "id": "c_045",
  "name": "裂石掌",
  "cost": 3,
  "tags": ["战斗"],
  "effects": [
    { "when": "reveal", "do": [{ "op": "gain", "res": "combat", "n": 2 }] },
    { "when": "agent",  "do": [
        { "op": "gain", "res": "troop", "n": 1 },
        { "if": { "influence": { "faction": "sword", "gte": 2 } },
          "then": [{ "op": "gain", "res": "combat", "n": 1 }] }
    ]}
  ]
}
```

**效果原语清单（约 28 个，覆盖 85% 的卡）**：

| 族 | 原语 |
|---|---|
| 资源 | gain / spend / convert（6 种资源：钱、特产 A、特产 B、部队、影响力、VP） |
| 牌库 | draw / discard / trash / search / shuffle / topdeck |
| 牌区 | acquire（买入）/ gain-to-hand / return-to-market |
| 工位 | place-agent / recall-agent / ignore-requirement / extra-agent |
| 战斗 | combat-bonus / retreat / post-combat-reward |
| 影响力 | influence+ / influence-set / alliance-check |
| 触发 | reveal / agent / combat-win / round-end / on-acquire |
| 控制 | if / choose / repeat / optional |

**长尾预算**：约 15% 的卡需要"独特原语"（一次性脚本）。这部分必须允许用逃生舱（内联 handler 函数）表达，否则会为了 3 张卡把 DSL 撑成图灵完备的语言——这是卡牌引擎最常见的死法。

### 3.4 状态与存档模型

采用**不可变 State + Command → Event**：

- 存档 = 初始 seed + 事件流（体积小、可回放、可审计）
- 断线重连 = 重放事件（免费获得）
- Bug 复现 = 拿到 seed + 事件流，100% 重现
- 平衡测试 = 同一 seed 跑不同 AI，对比结果

**随机性必须走 seeded PRNG**，且 RNG 调用次数要与事件一起记录，否则回放会漂移——这是此类项目最隐蔽的一类 bug。

### 3.5 所需资源

| 类别 | 需求 | 说明 |
|---|---|---|
| 人力（最小） | 1 人全栈 + AI 辅助 | 引擎、UI、内容、测试全包 |
| 人力（推荐） | 3 人：引擎/后端 1、前端 1、内容/美术 1 | 并行度最高，5–6 个月可上线 |
| 美术 | 程序化卡面模板 + 图像生成 + 统一风格规范 | 90 张卡面靠模板化，不要一张张画 |
| 现金 | **< ¥3 万**（MVP，不含人力） | 美术外包 ¥1–3 万；服务器 ¥300–1000/月 |
| 工具 | 无商业授权依赖 | 全开源栈 |

## 5. 主要技术难点与风险

### 5.1 五个真难点（按"会不会拖垮项目"排序）

**① 单人 AI —— 唯一的"极高"复杂度模块**

这不是普通的棋类 AI。每个决策点都是不同性质的子问题：

| 决策点 | 每回合次数 | 难度 | 原因 |
|---|---|---|---|
| 选哪张牌放特工 | 2–3 | 高 | 需要评估 20+ 工位 × 手牌组合 |
| 买哪张牌 | 1–2 | 中高 | 需要评估牌库长期价值，不只是当下收益 |
| 战斗投入多少 | 1 | 高 | 隐藏信息（对手手牌、阴谋牌） |
| 阴谋牌何时打出 | 0–2 | 高 | 反应式，时机窗口窄 |

**结论：不要一开始就上 MCTS。** 分层启发式（规则打分 + 权重调参）+ 自动对战调参，能到"中等人类玩家"水平；MCTS/神经网络是 1.0 之后的事。原因：MCTS 在隐藏信息 + 高分支（20 工位 × 5 手牌）下需要 determinization，工程量和调参成本会翻 3 倍以上。

**② 结算时序 —— bug 的主要来源**

卡牌游戏的 bug 有 70% 集中在三处：同时触发谁先结算、替代效果、循环触发。缓解手段只有一个：**在写代码前先写一张"时机表"**（Timing Chart），把每个触发点、结算顺序、优先级规则列成表，引擎按表执行。这张表是规则书的第一章，不是实现细节。

**③ 卡牌平衡 —— 没有终点，只有止损线**

60 张卡 × 平均 2.2 个效果 × 6 个触发时机，人工测不完。唯一可行路径是**自动对战 + 统计**：headless 引擎跑 10 万局，看每张卡的"胜率贡献"和"选取率"，把明显过强/过弱的卡拉回区间。这也反向要求 §3.1 的 headless 约束必须满足。

**④ 内容长尾 —— 最容易被低估**

前 60 张卡 2 周做完，后 30 张卡要 6 周。因为简单的资源/抽牌卡先被想到，剩下的都是"条件触发 + 多段结算 + 跨系统交互"。**排期时必须假设内容效率递减 50%。**

**⑤ UI 状态同步 —— 中等但磨人**

一个动作要经过"点击 → 预检 → 提交 → 引擎返回事件 → 播放动画 → 更新 UI"，任何一步没对齐就会出现"牌飞了但数字没变"。解法是**单向数据流 + 事件驱动动画**：UI 永远只根据事件流渲染，不允许自己算状态。

### 5.2 风险矩阵

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| AI 做不出"像人"的水平 | 中 | **高**（单人模式失去意义） | 先做基线 AI 打通闭环，把 AI 当独立里程碑验收；宁可"简单但合理"也不做"复杂但抽搐" |
| 内容量超支 | **高** | 中 | 首版砍到 60 卡；建立"卡牌成本分级"（简单/中等/复杂），排期按级配比 |
| 平衡失控 | 高 | 中 | 自动对战 + 明确的"可接受区间"（如单卡胜率贡献 45%–55%） |
| **IP 侵权** | 中 | **极高**（下架/诉讼） | 不用 Dune 名称/角色/图像/卡表；美术原创或商用授权；上线前做商标检索 |
| 单人项目动力衰减 | 中 | 高 | 每个阶段必须有"可玩产物"，不做纯基建 |
| 时序 bug 反复 | 高 | 中 | 时机表前置 + 属性测试（随机生成对局序列断言不变量） |
| 联机作弊 | 低（后置） | 中 | 服务端跑引擎，客户端只渲染；不做客户端权威 |

## 6. 与现有项目的可复用部分

**必须先说清楚一句：能复用的是"认知、数据和工具方法"，不是代码。** 现有工程是 Unity IL2CPP 逆向环境，新项目是 Web 全栈，二进制层面零复用。但下面这些是实打实能省时间的：

### 6.1 可直接复用（迁移成本低）

| 资产 | 复用什么 | 迁移方式 |
|---|---|---|
| **剧本 DSL 字段模型**（§逆向报告 4.1） | `EndgameTriggerScore` / `StartingDeck` / `StartingAgents` / 起始资源 / 牌堆排除 / 多局连战——这是一份**官方验证过的配置模型** | 直接映射成新项目的 `scenario.json` schema，省掉 1–2 周的设计 |
| **卡牌分类法** | Imperium / Intrigue / Contract / Conflict 四类 + 各自数量配比（130/62/28/23） | 作为新项目内容配比的基线参考 |
| **卡牌数据结构** | `{类别, 花费, 效果列表, 触发时机, 所属内容集}` | 这套字段是逆向确认过的，不用再试 |
| **事件日志式存档** | 官方存档含 `entities` + 803 条 `displayActions` | 直接采用为存档格式（§3.4） |
| **内容回读校验脚本思路** | 二次加载补丁包、逐字段断言 | 改写成 CI 里的 `content-lint`：schema 校验 + 引用完整性 + 数值区间检查 |
| **本地化键值表结构** | 12 语言 key-value | 新项目 i18n 直接沿用扁平 key 方案 |

### 6.2 可迁移的方法论（比代码值钱）

| 教训 | 迁移到新项目 |
|---|---|
| **先打点，再动手**（前 4 版都在猜 API，成本极高） | 新项目先写"观测优先"的调试面板：状态全量导出 + 事件流查看器，再写业务逻辑 |
| **编译期错误是资产** | 卡牌 schema 用 TypeScript 类型 + Zod 校验，让内容错误在写的时候就报 |
| **区分"工具错误"与"目标限制"** | 遇到 bug 先问"是我的代码错，还是设计本身有问题"，别急着推翻架构 |
| **读状态比拦事件简单一个数量级** | 引擎设计成"状态可全量快照"，调试一律从快照入手，不靠日志追 |
| **不要用 grep 判断压缩容器** | 对应新项目：不要靠肉眼看 UI 判断状态对不对，要看事件流 |

### 6.3 不可复用（含法律边界）

| 项 | 原因 |
|---|---|
| Unity 工程、AssetBundle、interop 程序集 | 技术栈不同，且属他人版权物 |
| 286 张卡的名字、文本、图像、数值 | 受版权保护 |
| Dune 世界观、角色、地名 | 受版权 + 商标保护 |
| BepInEx / Harmony 插件 | 新项目不需要注入，且这类技术不应带入商业产品 |

> **法律提示**：游戏**机制**（工人放置、牌库构筑、影响力轨道）通常不受版权保护，但**具体表达**（卡名、卡面文字、美术、UI 布局的独创性组合）受保护。安全做法是：机制层借鉴，表达层 100% 原创，且不做"整体观感"的高度模仿。上线前建议做一次商标与外观检索。

## 7. 分阶段推进建议与里程碑

### 7.1 阶段表

| 阶段 | 周期 | 产出 | 验收标准 | 关键决策 |
|---|---|---|---|---|
| **P0 规则定稿** | 2–3 周 | 规则书 v1（含时机表）+ 30 张卡表（CSV）+ 纸质原型 | 3 场纸质/桌游模拟器试玩，能打到分出胜负，无规则歧义 | 主题定稿、胜利点阈值、回合阶段数 |
| **P1 引擎内核** | 4–6 周 | headless 引擎，CLI 跑完整一局（脚本玩家 vs 脚本玩家） | 1000 局无崩溃；状态不变量断言全通过；seed 回放 100% 一致 | 事件模型、时序表落地方式 |
| **P2 单人可玩闭环** | 6–8 周 | Web UI + 基线 AI，人 vs AI 打到 10 VP | 未看过说明书的测试者能独立完成一局；单局 20–30 分钟 | UI 信息密度、动画取舍 |
| **P3 内容与平衡** | 6–8 周 | 60–90 卡 + 4 派系 + 8 领袖；10 万局自动对战报告 | 单卡胜率贡献落在 45%–55%；无"必选卡" | 长尾卡是否砍掉 |
| **P4 打磨与发布** | 4–6 周 | 音效、引导、存档、设置；Web 免费版或 Steam 抢先体验 | 崩溃率 < 0.5%；新手 3 分钟内理解第一回合 | 商业模式 |
| **P5 联机（可选）** | 6–8 周 | 服务端权威 + 匹配 + 断线重连；或先做异步对战 | 100 局联机无不同步 | 同步 vs 异步 |

**总周期（单人）**：P0–P4 合计 **22–31 周 ≈ 5.5–7.5 个月**，加缓冲取 9 个月。
**总周期（3 人）**：P1–P3 可部分并行，**18–24 周 ≈ 4.5–6 个月**。

### 7.2 里程碑（可对外承诺的节点）

| 里程碑 | 时点（单人基准） | 含义 |
|---|---|---|
| **M1 规则冻结** | 第 3 周 | 规则不再改，之后只改数值 |
| **M2 机器能打完一局** | 第 9 周 | 引擎可信，可以开始批量测试 |
| **M3 人能打完一局** | 第 17 周 | 产品成立，可以给外部人玩 |
| **M4 内容达标** | 第 25 周 | 有重玩性，可以谈发布 |
| **M5 可发布** | 第 31 周 | 崩溃率、引导、存档齐备 |
| **M6 联机** | 第 39 周 | 可选，不影响主体交付 |

### 7.3 明确不做（范围守则）

- ❌ 3D 棋盘、粒子特效、角色立绘动画
- ❌ 实时对战、语音、观战
- ❌ 排位赛季、成就、卡牌皮肤、战斗通行证
- ❌ 剧情战役（首版最多做 8 关的线性挑战）
- ❌ 用户自建卡牌 / 创意工坊（可作为 1.0 后的差异化，但会引入审核与平衡灾难）
- ❌ 移动端原生 App（Web 响应式先覆盖）

## 8. 决策建议

**如果是我，前 90 天会这么做：**

1. **第 1–3 周**：不写一行代码。写规则书 + 时机表 + 30 张卡，用 Tabletop Simulator 或纸片自测 3 局。目的：验证"这个玩法我自己觉得好玩吗"——这是唯一无法用工程手段补救的风险。
2. **第 4–9 周**：写 headless 引擎，用两个随机玩家跑 1000 局。目的：拿到一个**可信的规则实现**，后面所有工作都建立在它上面。
3. **第 10–13 周**：写最简 UI（能看能点即可，不做美化）+ 启发式 AI。目的：第一次"自己完整玩一局"。
4. **第 13 周做一次 go / no-go 判断**：如果这一局玩下来"没有想再玩一局"的冲动，问题在玩法设计，不在实现——此时改设计的成本是 1 周，等到 P3 之后就是 3 个月。

**三条最容易踩的坑，提前说：**

- **不要先做 UI**。UI 是最容易获得成就感、也最容易掩盖"引擎不对"的部分。先让机器能打完一局。
- **不要先做联机**。联机会把"引擎 bug"变成"网络不同步"，调试成本 ×5。单机闭环先跑通。
- **不要一上来做 100 张卡**。前 30 张卡会推翻 3 次引擎设计，做完 30 张再定 schema。
